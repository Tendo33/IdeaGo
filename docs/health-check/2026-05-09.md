# IdeaGo 仓库健康检查（2026-05-09）

**整体健康评分：82/100。** 匿名本地部署主线、FastAPI/LangGraph 后端、React/Vite 前端和测试基线整体清晰，但外部证据 URL 的前端安全边界、运行中状态恢复、以及少量分支契约漂移仍会影响面向用户的可信度。

**Top Issues Summary**

- P1：外部来源/LLM 生成的 URL 在报表 UI 中直接作为 `href` 渲染，存在点击型 XSS/恶意协议风险。
- P2：运行中任务状态仍主要依赖进程内内存；进程重启后用户会经历最多 180 秒 ping 后才得到“stale processing”错误。
- P2：未挂载的 legal 页面文件仍保留 hosted/account/Stripe fallback 文案，和 `main` 分支匿名个人部署契约不一致。
- P2：图表点击处理里有显式 `any`，局部突破了前端 strict/type-safety 约束。

**Risk Summary**

当前核心链路（提交 idea -> `/reports/new` -> SSE -> 报告 -> 历史/导出）结构完整，且 API fallback 顺序和 CSRF/rate-limit 基线较好。主要风险不是大面积架构失控，而是“外部非可信数据进入 UI”与“本地内存状态丢失后用户体验退化”。这些问题不会阻断所有使用，但会在公开部署、异常重启、或恶意 evidence payload 出现时放大。

**Recommended Next Actions**

1. 先修复报表外链协议白名单，覆盖 competitor/evidence/pain links。
2. 将 processing status 的 stale 判定前移到 `/status` 或 report detail 响应，避免前端长时间等待不存在的运行态。
3. 清理 `main` 分支 legal fallback 文案与显式 `any`，保持匿名分支契约和类型约束一致。

## 1. 执行摘要

本次按 `repo-health-check` 技能以 `exhaustive` 模式执行。覆盖范围包括 `.trellis/spec/` 项目契约、后端 API/cache/pipeline/source orchestration、前端 home/history/report/SSE 流程、测试与交付脚本。未逐行审计所有测试 fixture 和所有 source provider 的每个 HTTP 参数分支；主要深读了用户路径、持久化路径和安全边界。

项目目标是匿名用户提交创业 idea，系统通过 Tavily、Reddit、GitHub、HN、App Store、Product Hunt 等 live evidence 生成决策优先的验证报告。`main` 分支必须保持匿名/个人部署，不引入 auth、Supabase、Stripe、LinuxDo、profile、quota、admin、billing 等 hosted-only 依赖。

## 2. 项目全局健康度与架构评估

架构总体健康。后端在 `src/ideago/api`、`cache`、`pipeline`、`sources`、`models` 间边界清楚，前端在 `frontend/src/features`、`lib/api`、`lib/types` 间也基本符合 spec。Source Intelligence V2 的核心约束（`merger.py` 负责 deterministic dedupe，`aggregator.py` 负责 whitespace/opportunity synthesis）被保留。

扩展性主要受两点限制：第一，匿名本地部署的运行态由进程内 map 管理，适合单进程个人部署但不适合多 worker 或频繁重启；第二，前端 report 页面承载了较多 orchestration 状态，测试覆盖不错，但错误恢复分支已经较复杂。

技术债地图：运行态恢复属于中期可靠性债；URL 安全属于应立即修复的边界问题；legal fallback 和 `any` 属于契约/类型卫生债。

## 3. 产品逻辑与业务流审查

核心业务闭环成立：`HomePage` 提交后跳转 `/reports/new`，`ReportPage` 用 `new` 作为 transient route 启动分析，再 replace 到真实 `/reports/{id}`；后端 `POST /api/v1/analyze` 生成 report id 并启动后台 pipeline；前端 `useSSE` capped reconnect 后 fallback 到 `/status`。

流失点主要在异常恢复：如果服务进程在 pipeline 中途重启，status 文件可能仍是 `processing`，但内存里没有 `ReportRunState`/task。`_stream_events()` 会先持续 ping 最多 180 秒，然后才返回 `PIPELINE_PROCESSING_STALE`。这避免无限挂起，但用户仍会等待过久。

商业价值层面，报告顺序与 SectionNav 基本匹配：recommendation/why-now/pain/commercial/whitespace/competitors/evidence/confidence。直接竞品为空时的 fallback 文案较保守，没有把空结果误报成强蓝海，这是正确方向。

## 4. 前端 UI/UX 与操作流程体检

### [P1] 报表外链缺少协议白名单

- Location: `frontend/src/features/reports/components/CompetitorCard.tsx:27`, `frontend/src/features/reports/components/EvidenceSummaryPanel.tsx:148`, `frontend/src/features/reports/components/PainSignalsCard.tsx:151`
- Impact: 非可信 source/LLM payload 若包含 `javascript:`、`data:` 等 URL，用户点击报表里的外链可能触发浏览器执行或跳转到恶意协议。
- Evidence: 组件直接将 `link`、`item.url`、`url` 赋给 `<a href=... target="_blank">`；当前只做非空字符串检查，没有统一协议过滤。
- Confidence: 高。数据来自外部 API 与 LLM extraction，必须视为非可信。
- Recommendation: 增加共享 `sanitizeExternalUrl()`，只允许 `http:`/`https:`，并让不安全 URL 不渲染为可点击链接。

### [P2] `SectionNav` 和报告内容状态已复杂，后续改动容易破坏锚点一致性

- Location: `frontend/src/features/reports/components/ReportContentPane.tsx:96`, `frontend/src/features/reports/components/SectionNav.tsx:15`
- Impact: spec 要求 SectionNav anchors 与报告 sections 一一对应。当前有测试覆盖，但 section 列表由多个条件动态拼接，后续新增区块时容易漏掉 id 或条件。
- Evidence: `ReportContentPane` 通过 `hasWhyNowSection`、`hasCompetitorSection` 动态拼接 nav；`ReportCompetitorSection` 内部持有 `section-competitors` id。
- Confidence: 中。当前测试已有相关断言，因此是维护风险而非已确认 bug。
- Recommendation: 保持新增 section 必须同时更新 nav + render + test 的约束；可将 section metadata 收敛成单一数组。

### [P2] Legal 页面 fallback 文案与 `main` 分支契约漂移

- Location: `frontend/src/features/legal/TermsPage.tsx:43`, `frontend/src/features/legal/TermsPage.tsx:51`
- Impact: 即使页面当前未挂载，文件中仍存在 account/Stripe fallback 文案，后续一旦路由恢复会误导个人部署用户，并违反 `main` 不引入 hosted runtime 概念的 guardrail。
- Evidence: fallback 文案提到 “User Accounts” 和 “Paid plans are billed through Stripe”；locale JSON 已经是 personal deployment 文案，说明组件 fallback 过期。
- Confidence: 高。
- Recommendation: 同步 fallback 文案到 locale 里的匿名个人部署表述。

### [P2] 图表点击处理显式使用 `any`

- Location: `frontend/src/features/reports/components/LandscapeChart.tsx:149`
- Impact: 局部跳过 TypeScript 约束，可能让 Recharts click payload 与内部 chart point 混淆，未来升级时更难发现类型漂移。
- Evidence: 文件中有 `// eslint-disable-next-line @typescript-eslint/no-explicit-any` 和 `(entry: any) => handleClick(entry)`。
- Confidence: 高。
- Recommendation: 用本地 chart point 类型或窄化函数替代 `any`。

## 5. 后端架构、代码质量与安全

### [P2] Processing status 缺少快速 stale 恢复

- Location: `src/ideago/api/routes/analyze.py:193`, `src/ideago/api/routes/analyze.py:201`, `src/ideago/api/routes/reports.py:88`
- Impact: pipeline 进程重启或 task 丢失后，用户可在 SSE 中等待最多 180 秒才收到 stale error；`/reports/{id}` 与 `/status` 仍会报告 `processing`。
- Evidence: `_stream_events()` 在无 `run_state` 但 status 为 `processing` 时循环 ping 到 `_STATUS_ONLY_MAX_PINGS`；report detail/status 没有检查 status updated_at 与本地 task 是否存在。
- Confidence: 高。
- Recommendation: 在 status/read 路径中基于 `updated_at` + `is_report_id_processing()` 返回 `failed`/stale runtime 状态，或让 frontend fallback 更早触发。

### [P2] Rate limit 和 runtime state 是进程内实现

- Location: `src/ideago/api/app.py:37`, `src/ideago/api/dependencies.py:36`
- Impact: 单进程个人部署可接受；多 worker 或重启后，rate-limit、dedupe、task/subscriber 状态不可共享，可能导致重复 pipeline 或限流失效。
- Evidence: `_rate_limit_store`、`_report_runs`、`_processing_reports`、`_pipeline_tasks` 都是模块级 dict。
- Confidence: 高。
- Recommendation: 继续把它标为 personal deployment 限制；若发布多 worker 配置，需要迁移到 SQLite/Redis 或明确禁止多 worker。

### [P3] 后端模块注释仍有 hosted/PostgreSQL 遗留语义

- Location: `src/ideago/pipeline/langgraph_engine.py:3`, `src/ideago/pipeline/langgraph_engine.py:35`
- Impact: 注释提到 PostgreSQL/Supabase 生产 checkpointer，但 `main` runtime contract 是 local SQLite checkpoints；这会误导后续维护者把 hosted-only 配置带回 main。
- Evidence: docstring 写 “PostgreSQL checkpointer (via Supabase DB) for production”，构造器也保留 `checkpoint_db_url` 参数。
- Confidence: 中。当前 `dependencies.py` 没有传入 hosted DB URL，因此不是运行时 bug。
- Recommendation: 清理注释或明确该参数不是 `main` 默认运行路径。

## 6. 测试、可观测性与交付风险

测试覆盖面较好：后端有 API、cache、settings、source、pipeline、LangGraph regression；前端有 API/SSE/report/history/component tests。交付脚本也明确使用 `uv` 与 `pnpm`。

主要缺口是外部 URL sanitization 的前端安全回归测试，以及 process restart/stale processing 的 API-level regression。可观测性方面，pipeline 有 structured observability event，但 stale processing 和 source-level degradation 仍更偏日志，不是用户可直接理解的恢复状态。
